# 08｜Claude Code、Codex 与 LangChain：先判断你在选哪一层

> 核对日期：2026-09-15。本文根据当前官方文档比较定位与工作方式；不把某次体验当性能排名，也不假设不同入口、套餐或操作系统的功能完全相同。

## 1. 最容易混淆的一句话

“我做 Agent，应该选 Claude Code、Codex 还是 LangChain？”这句话缺少一个条件：**你要使用一个能帮你工作的 Agent，还是开发一个提供给用户的 Agent？**

Claude Code 与 Codex 提供面向开发工作的产品和执行环境；LangChain、LangGraph 提供构建应用的程序库与运行机制。它们可以配合使用。例如让 Codex 帮你写一个使用 LangChain 的 FastAPI 服务，这并不矛盾。

可以把成品编程 Agent 类比为配好工具的工作台，把框架类比为搭工作台的部件。类比的边界是：成品也能通过 SDK、脚本和扩展集成；框架也有预设能力，实际边界不是绝对的。

## 2. 四者分别负责什么

| 对象 | 官方定位和主要职责 | 你通常仍需决定什么 |
| --- | --- | --- |
| Claude Code | 编程 Agent 工具；读取代码、修改文件、运行命令、连接开发工具 | 任务范围、项目约定、权限、验收标准 |
| Codex | 编程 Agent 产品；本文以 CLI 的代码检查、编辑、命令执行和自动化为具体例子 | 工作目录、执行边界、测试与审查标准 |
| LangChain | 构建模型应用的框架；当前 `create_agent` 提供可配置的 Agent harness | 业务工具、上下文、行为规则、错误处理 |
| LangGraph | 面向长期运行、有状态 Agent／工作流的底层编排框架与运行时 | 状态结构、节点、转移条件、持久化与恢复策略 |

依据分别来自 [Claude Code 概述](https://code.claude.com/docs/en/overview)、[Codex CLI 官方文档](https://learn.chatgpt.com/docs/codex/cli)、[LangChain 概述](https://docs.langchain.com/oss/python/langchain/overview)与 [LangGraph 概述](https://docs.langchain.com/oss/python/langgraph/overview)。表中“仍需决定”的内容是根据职责边界给出的工程建议。

其中 **harness** 是围绕模型组织上下文、工具和执行过程的系统，见 [第 09 篇](09-harness.md)。模型能产生工具调用建议，真正运行工具、记录状态和限制权限的是外围程序。

## 3. 用同一个需求看两种工作

需求：“给客服做一个工单助手，读取知识库和工单，生成处理草稿，获得必要授权后才能修改工单状态。”

### 开发阶段：编程 Agent 帮你改项目

你可以让 Claude Code 或 Codex 阅读 FastAPI 路由、定位认证逻辑、实现查询接口、运行测试，再检查差异。它的工具可能是读文件、搜索、编辑与终端。输出是代码修改、测试结果和解释。

不要只说“实现一个 Agent”。更有用的任务描述是：

```text
为工单助手增加草稿接口。复用现有认证与租户校验。
只读取当前用户可访问的工单和知识库。
生成草稿不修改工单；实际修改走已有授权流程。
验证跨租户拒绝、资料不足与工具失败的行为。
```

这里具体的路由与认证实现必须先读项目确认；这是需求示例，不代表本仓库已经有这些接口。

### 运行阶段：你的应用服务客服

上线后，客服请求进入 FastAPI。服务端确定身份和租户，调用只允许访问相应数据的工具，再让模型生成草稿。需要执行修改时，服务端校验动作、参数和授权，再记录结果。

```text
客服 → FastAPI 身份校验 → Agent／确定性流程
                          ↓
                     工单与知识库工具
                          ↓
                 草稿 → 授权校验 → 修改
```

这一层可先用模型 SDK 和普通 Python 完成。如果有多提供商适配、通用工具循环等明确需求，考虑 LangChain；如果流程需要等待人工、暂停后恢复、持久化状态和复杂分支，考虑 LangGraph。采用框架后，租户权限与业务一致性仍由你的服务负责。

## 4. LangChain 与 LangGraph 的关系，别背旧结论

当前 LangChain 官方文档以 `create_agent` 为重要入口，支持通过中间件逐步加入路由、工具规则等能力；其 Agent 建立在 LangGraph 上，利用后者的持久执行和人工参与等机制。[来源：LangChain 概述](https://docs.langchain.com/oss/python/langchain/overview)

LangGraph 可以与 LangChain 组件一起使用，也可以独立使用。它能在同一个图中混合确定性的程序步骤和由模型决定的步骤。[来源：LangGraph 概述](https://docs.langchain.com/oss/python/langgraph/overview)

把它理解成“流程图”还不够：重点是**每一步操作什么状态、何时继续、失败后从哪里恢复**。例如等待审批两天，应保存可恢复状态，而不是让一次 HTTP 请求或一个 Python 函数一直占着连接等待。

框架提供恢复机制也不代表外部写入自动“只执行一次”。如果数据库已经更新、执行状态却尚未保存，恢复时可能再次进入该步骤。业务工具仍需幂等键、唯一约束或版本控制；不能把“有检查点”理解成“跨所有外部系统的事务”。

当前官方概述还列出 Deep Agents 作为包含更多预设能力的上层方案，例如自动上下文压缩、虚拟文件系统和子 Agent。这里知道它的定位即可；不用为了学基础把所有生态组件都装一遍。[来源：LangChain 概述](https://docs.langchain.com/oss/python/langchain/overview)

## 5. 成品编程 Agent 怎么选才有依据

Claude Code 官方概述列出终端、IDE、桌面和浏览器入口；Codex 官方 CLI 页面说明本地读写文件、运行工具、交互和脚本自动化，并链接 IDE、桌面与云端入口。这只能说明产品提供这些形态，不能推出各入口拥有相同能力。[Claude Code](https://code.claude.com/docs/en/overview)｜[Codex CLI](https://learn.chatgpt.com/docs/codex/cli)

对实际工作更有意义的是，用相同仓库版本、任务和验收标准进行比较：

| 观察项 | 具体检查 |
| --- | --- |
| 改动正确性 | 原问题是否解决，有没有引入新问题 |
| 理解上下文 | 能否找到真正调用路径和项目约定 |
| 工具可靠性 | 命令是否真的运行，错误后怎样恢复 |
| 权限可控性 | 能否限制数据与操作范围、检查关键动作 |
| 协作体验 | 能否查看差异、补充约束、审查和恢复工作 |
| 总成本 | 完成任务的费用、耗时和人工返工 |

只对比“生成了多少行代码”容易奖励错误行为：复制一套认证比复用现有认证代码更多，却可能更差。选型指标应奖励满足需求与减少缺陷。

比较时记录产品版本、模型配置、入口、权限、时间与费用范围；不同设置会改变结果。没有这些条件的“某工具永远更强”，通常无法复现。

## 6. 三个容易在工作中踩的坑

**本地运行，不等于数据不出机器。** CLI 的文件操作位置与模型推理位置是两件事。接入云模型、远程 MCP 或日志服务都可能产生数据传输。具体保留、训练使用、区域和账号条款，应核对采用的产品、供应商及组织配置，不能从“CLI”或“开源”两个词推断。

**统一接口，不等于模型无差别替换。** LangChain 能减少适配工作，但不同提供商的工具调用、状态、结构化输出与费用仍有差异；更换后仍需评测，见 [第 07 篇](07-multi-model-switching-cost.md)。

**框架功能，不等于业务已经完成。** 有“人工参与”能力，你仍需决定谁有权审批、审批哪一个动作、数据变化后是否失效。否则流程看似可控，实际仍可能误操作。

## 7. 面试回答与小练习

**问：LangChain 和 Codex 有什么区别？**

Codex 是可以直接用于开发任务的编程 Agent 产品；LangChain 是构建自有 Agent 应用的框架。前者主要帮助开发者完成工作，后者让开发者定义模型、工具与业务行为。两者可以配合，比较时要先明确是在选择开发工具还是应用实现方式。

**追问：为什么不用 LangGraph 做所有 AI 功能？**

固定的“检索一次再生成”通常用普通函数即可清楚表达。LangGraph 的价值在于状态、暂停恢复与复杂编排等需求；引入后也要维护状态结构和流程。依据当前需求选择，不能因为画得出一个图就必须加框架。

**练习：**你的功能只有读取一条工单并生成摘要，需要三个 Agent 和 LangGraph 吗？

**参考答案：**通常先不需要。由服务端完成身份与数据权限校验，查询后调用模型即可。若后续出现跨多次请求的人工审批、复杂分支和可靠恢复需求，再评估编排框架。无论使用什么产品或库，都要验证生成结果是否有依据、是否遗漏关键信息。

进一步练习见 [面试题与解析](10-interview-questions-and-answers.md)。所有功能范围与价格应按实际采用的版本和账号复核；本文不声称不同产品支持范围完全一致。
