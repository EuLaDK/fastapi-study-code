# 02｜记忆、RAG 与长上下文：信息究竟放在哪里？

> 本文依据主题重新编写。默认你知道 API 如何接收请求，不要求机器学习背景。资料核验日期：2026-09-15。

## 先看问题：为什么模型“看过”还是会答错？

FastAPI 工单助手昨天读过一份退款政策，今天又说错了期限。可能的原因至少有三种：今天的请求没带昨天的信息；检索找到了旧版本；模型拿到了正确政策，却忽略了例外条件。三者分别属于信息保存、信息选择和信息使用问题，不能统一归咎于“模型记性不好”。

**本章的本质：记忆决定什么值得保存，检索决定本次取什么，上下文决定模型本次实际能看到什么。** 它们可以配合使用。

## 1. 先画清三种存放位置

| 信息位置 | 是什么 | 如何更新 | 典型边界 |
|---|---|---|---|
| 模型参数 | 训练形成的统计模式与知识 | 训练、微调等改变参数的过程 | 普通聊天写入不等于更新权重 |
| 本次上下文 | 当前推理请求可用的指令、历史、资料和工具结果 | 应用或服务组织本次输入 | 容量有限，放进去也不保证正确使用 |
| 外部存储 | 数据库、文件、搜索索引、业务系统 | 程序按权限读写 | 存下来的信息还要被取回才有作用 |

“长期记忆”在 Agent 工程中常指外部持久化内容，并非模型永久学会了这些事实。即使 API 替你维护会话，概念上也应分清会话状态和模型权重。[来源 1](https://arxiv.org/abs/2005.11401) 区分了参数化知识和外部非参数化记忆；[来源 3](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 介绍了把笔记持久化后按需重新读回上下文的方法。

可以类比为：模型已有的知识是训练所得，本次上下文是桌面摊开的材料，外部存储是档案柜。档案柜很大，不表示每次工作时所有档案都摊在桌上；这个类比只解释信息位置，不说明模型像人一样记忆。

## 2. RAG：先找证据，再带着证据回答

RAG 即 Retrieval-Augmented Generation，检索增强生成。原始论文研究了预训练生成模型与外部密集向量索引结合的训练方案；今天工程中常把“检索外部资料，再提供给模型生成”的流程广义称为 RAG。两者不能混为同一个固定算法。[来源 1](https://arxiv.org/abs/2005.11401)

```mermaid
flowchart LR
    A[问题与当前用户身份] --> B[在授权范围内检索]
    B --> C[筛选相关且有效的证据]
    C --> D[组装问题与证据]
    D --> E[生成带依据的回答]
    E --> F[校验引用与业务规则]
```

一条常见的知识库流水线包含两个阶段：

1. **资料准备：** 收集经过批准的资料，保留标题、来源、版本、适用产品、有效时间和权限信息，再建立搜索索引。长文档可以按语义段落切块，但应让例外条款和它约束的规则保持关联。
2. **问题处理：** 根据问题和用户权限取候选资料，必要时重排，选择可用证据，生成答案并核验引用。

“切块”是把长文拆成便于搜索的片段。太小会丢上下文，太大容易掺入无关内容；没有适用于全部文档的固定最佳长度。“重排”是对候选资料再比较相关性，它只能重排已经找到的候选，不能凭空补回没召回的文件，而且会增加延迟。是否使用应由样本测试决定。

RAG 也不等于向量数据库。工单号、错误码适合精确匹配；同义表达可能适合语义检索；字段明确时直接查 SQL 就够了。向量相似度反映某种表示空间里的接近程度，不等于事实正确、政策有效或用户有权访问。

## 3. 用一张工单理解“有引用仍然答错”

用户问：“我的订单申请退款已经五天，为什么还没到？”检索可能返回：

| 证据 | 内容 | 能支持什么 |
|---|---|---|
| 当前退款政策 | 审核通过后按规定时限处理 | 一般处理规则 |
| 工单正文 | 用户说五天前提交申请 | 用户陈述的申请时间 |
| 订单系统 | 尚未取得审核状态 | 不能支持“审核已经通过” |

如果回答“通常五天到账，你的退款应已完成”，就是把申请时间当成审核通过时间，又把一般规则当成订单事实。即使后面挂着政策链接，推断仍然不成立。

可接受的草稿应区分三部分：政策写了什么、这张订单已知什么、还缺什么。引用的价值是让结论能被追溯与核查，不是装饰。

权限也必须在模型之外处理：检索阶段限制可搜索的租户与资料，返回上下文前再次确保记录可见。不要先把其他客户资料交给模型，再指望一句“不要泄露”补救。技术安全边界见[第 03 章](03-tool-call-hitl-security.md)。

## 4. 长上下文能替代 RAG 吗？

如果资料少、来源明确、用户本来就有权限，直接把全文放进上下文通常更简单。例如比较两份短政策，不一定需要建立向量索引。

如果资料很多、频繁更新、有租户隔离要求，按需检索依然有意义。长上下文增加的是可容纳材料的上限，不能自动解决版本筛选、权限、成本和证据冲突。

| 情况 | 合理起点 | 原因 |
|---|---|---|
| 两三份短文，要跨段比较 | 全文上下文 | 避免切块漏掉关联条件 |
| 数量庞大的产品知识库 | 检索后提供相关章节 | 减少无关信息，便于更新与权限控制 |
| 用户交来一份长合同，要分析整体关系 | 先评估全文或分章节处理 | 只搜局部片段可能遗漏全局依赖 |
| 明确的一张订单状态 | 查权威业务 API | 文档不能替代实时业务状态 |

《Lost in the Middle》在其测试的模型和任务中发现，证据放置位置会影响效果，中间位置可能明显较差。[来源 2](https://arxiv.org/abs/2307.03172) **这是特定时期、模型和实验条件下的结果，不能推断所有 2026 年模型都必然同样退化。** 它提醒我们：评估时除了测试“能装多少”，还要测试“能否找到并正确关联所需信息”。

比较 RAG 和全文输入时，应使用相同业务题、明确的答案依据，记录正确率、遗漏率、延迟与实际费用。只有一个“针在草堆里找到了”的演示，不能证明系统能够正确处理多条冲突政策。

## 5. 记忆应保存事实和状态，而不是无差别保存聊天

对工单助手，值得持久化的内容可能是工单 ID、已经确认的事实、来源版本、待核实项和草稿位置。当前查询结果和用户偏好也有不同寿命：订单状态可能很快变化，回复语言偏好则可能较稳定。

工程建议是给记忆保存主体、来源、时间和适用范围；对动态事实设置重新查询规则。用户说“我应该可以退款”只能存为用户陈述，不能变成系统确认的“符合退款条件”。

摘要是一种有损压缩。把几十轮对话压成“已核实退款”，可能漏掉“只核实了一般政策”。更稳妥的摘要应留下：

```text
目标：为 T-104 起草回复，不发送。
已确认：工单描述申请时间；当前政策版本 P-7 已读取。
未确认：审核通过时间、银行到账状态。
证据：工单与政策的可回查标识。
下一步：若业务 API 可用，查询状态；否则明确资料不足。
授权状态：以独立的授权记录为准，不从摘要推导执行权限。
```

Anthropic 的上下文工程文章讨论了 compaction（压缩）、持久化笔记与子任务隔离，也明确指出过度压缩会丢失后来才显得关键的信息。[来源 3](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 因此关键金额、审批状态和执行记录应以结构化业务数据为准，不能只靠模型摘要。

## 6. 出问题时按三个层次定位

第一层，**资料是否存在且有效？** 当前知识库没有政策，就不是换 embedding 模型能解决的问题。

第二层，**正确资料是否进入候选和最终上下文？** 在标注了正确证据的题集中，可以观察 Recall@k：前 k 条候选覆盖了多少应有的相关证据。指标高也不等于回答一定正确。

第三层，**回答是否被证据支持？** 检查关键结论能否从引用中推出、有无遗漏例外、是否把缺失信息写成确定事实。必要时让人工对高风险样本核验，模型自评只能作为辅助。

这三层对应资料治理、检索和生成。只有定位到失败层，调整切块、重排、模型或提示词才有针对性。

## 7. 面试表达与小练习

**面试问：有了百万级上下文，RAG 还有必要吗？**

可以答：“要看资料量、更新频率、权限和任务。全文上下文能减少检索遗漏，但大窗口不保证所有材料被准确使用；RAG 能选择相关和授权资料，但存在检索漏失。先用业务题比较效果和成本，也可以检索定位后加载完整章节，组合两者。”这里的“百万级”是题设，不是对某个当前产品额度的声明。

**练习：** 检索第一名是旧政策，第二名是现行政策。把 top-k 从 2 提到 10，能解决问题吗？

**参考答案：** 不能保证。正确版本已经在候选中，问题可能是版本筛选与生成时的证据优先级。先用有效期、适用产品和批准状态选择权威资料，再检查回答是否引用当前版本；如果多个版本分别适用不同时间段，应依据业务发生时间匹配，而不是简单永远选最新。
