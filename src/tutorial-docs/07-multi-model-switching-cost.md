# 07｜多模型切换与成本：算清“把事情做对”需要多少钱

> 核对日期：2026-09-15。本文解释选择方法，不提供长期有效的模型排行榜。产品可用性、价格、缓存规则会变化，实际采购和上线需重新核对官方页面。

## 1. 从一个真实问题开始

工单助手有两种请求：“查询工单状态”和“综合三份冲突的故障记录，拟定处理方案”。如果都使用同一种配置，可能简单任务花钱过多，也可能复杂任务反复失败。

**多模型路由的本质，是把不同任务交给满足质量要求、总成本合适的模型配置。** 配置不仅是模型名字，还包括推理强度、上下文、工具、服务档位等。它像给工作安排合适的人，但模型没有稳定的人类资历：在你的任务上是否合适，要靠评测确定。

先区分三个概念：

| 概念 | 改变什么 | 工单例子 |
| --- | --- | --- |
| 模型路由 | 一次请求交给谁处理 | 普通分类用 A，复杂分析用 B |
| 失败回退 | 原路径失败后走哪条恢复路径 | A 服务不可用，转到经过验证的 B |
| 多 Agent | 有多少独立任务状态、角色和协作过程 | 检索员与分析员分别调查，再汇总 |

一个 Agent 可以先后调用不同模型；多个 Agent 也可以使用同一个模型。**模型数量与 Agent 数量不是同一个维度。** 多 Agent 的协调成本见 [第 01 篇](01-react-plan-execute-multi-agent.md)。

## 2. 先做一个基线，再考虑路由

工程上先选一个能完成任务的配置，整理一组有代表性的工单，记录正确率、越权次数、耗时和费用。这里的“正确”应包含业务约束：找到工单却泄露其他租户资料，仍然失败。

最初几十个样本适合发现明显问题，不能证明生产质量。按简单查询、模糊需求、资料冲突、工具异常等类别分别查看结果；否则大量简单题会掩盖困难场景的失败。

有了证据，再增加最简单的路由：

```text
查状态 → 受权限约束的查询工具 → 短回答
需要综合证据 → 检索资料 → 较强配置生成草稿
涉及状态修改 → 服务端校验与必要审批 → 执行
```

这是工程建议，不是某个厂商保证有效的固定架构。路由依据优先使用明确的任务类型、所需模态、工具能力和长度限制；不要把模型自报“信心 95%”当成经过校准的概率。

强模型也可能缺资料，增加推理强度不会自动补齐工单历史。先确认失败属于模型能力、检索、工具还是权限，避免花更多钱重复同一个错误。

## 3. 为什么切换模型不是改一个字符串

SDK 的统一接口可以减少调用代码差异，却不能消除能力和语义差异。

| 检查项 | 忽略后的后果 |
| --- | --- |
| 工具调用、结构化输出、图片等能力 | 请求被拒绝，或返回无法执行的文本 |
| JSON Schema 支持范围与参数约束 | 同一工具定义在另一模型上不能使用 |
| 上下文和输出限制 | 历史被截断，输出无法包含必要信息 |
| 会话、推理状态、缓存兼容性 | 换模型后重新处理上下文，或丢失必要状态 |
| 数据传输范围和授权 | 回退把工单发送到尚未批准的供应商 |

应用应保存**业务状态**：用户目标、已核实事实及来源、工单版本、工具执行结果、待执行动作。模型内部状态、供应商会话 ID 或加密推理块，不能默认跨供应商使用。能传递给下一模型的是双方接口支持的内容，不是“整个脑子”。

例如交接信息可以是：“工单 T-42，版本 7；资料 A 与 B 冲突，尚未确认根因；已查询日志；草稿已生成；尚未获准修改状态。”事实必须能回查，摘要也可能漏信息。审批应保存在可信服务端，并绑定具体动作、参数和有效条件，不能让模型转述一句“已批准”就继承权限。

## 4. 成本至少分成四本账

**第一本：模型用量。** 对按 token 收费的文本调用，可以使用下面的核算思路。各类 token 必须互斥，单价按当次模型和服务档位确定：

```text
模型费用 = 普通输入量 × 普通输入单价
         + 缓存读取量 × 缓存读取单价
         + 单独计费的缓存写入量 × 写入单价
         + 计费输出量 × 输出单价
```

若模型不单独计费缓存写入，相关输入按其普通规则计算；不要重复加一次。OpenAI 当前官方文档已经区分部分模型的缓存写入与读取费用，因此不能把“缓存永远免费写入”当成通则。[来源：缓存指南](https://developers.openai.com/api/docs/guides/prompt-caching)

OpenAI 的推理 token 会计费，但通常不能通过最终回答直接看到；它们计入输出用量，不能在输出总量之外再加一遍。[来源：Reasoning models](https://developers.openai.com/api/docs/guides/reasoning#how-reasoning-works)

**第二本：工具与基础设施。** 搜索、容器、检索存储、数据库、日志可能另收费。官方价格页也把模型和工具分开列出。[来源：API Pricing](https://developers.openai.com/api/docs/pricing)

**第三本：失败和重试。** 每次重试都可能重新发送很长的历史；便宜模型多走几轮，可能更贵。

**第四本：人工处理。** 错误草稿要人修，误操作要恢复。人工时间可以单独统计；除非有可信的人时单价，否则不要硬凑成精确货币值。

### 算一笔明确的示例账

以下全部是**教学虚构单价，单位为美元／百万 token，不是任何真实模型报价**：

| 类别 | 用量 | 单价 | 费用 |
| --- | ---: | ---: | ---: |
| 普通输入 | 12,000 | 2.00 | 0.0240 |
| 缓存读取 | 8,000 | 0.20 | 0.0016 |
| 单独计费缓存写入 | 0 | 2.50 | 0 |
| 计费输出 | 1,000 | 8.00 | 0.0080 |
| 合计 | — | — | 0.0336 |

这是一次调用的模型费用，不包含工具和重试。缓存也不是答案缓存：它复用相同前缀的计算结果，模型仍生成新回答。改变模型、工具定义或前缀内容可能影响命中，应读取实际缓存用量，不能凭“提示词差不多”估算。[来源：缓存指南](https://developers.openai.com/api/docs/guides/prompt-caching)

## 5. 更有用的指标：每个成功任务的成本

```text
每个成功任务成本 = 同一批任务的总费用 / 经验证成功的任务数
```

仍用虚构数据：同样 100 个工单，A 总花费 20 元、成功 50 个，得到 0.40 元／成功任务；B 总花费 30 元、成功 90 个，得到约 0.33 元／成功任务。单次更贵的配置可能更划算。

但这个比值不能单独决定上线。剩余失败需要怎样处理、错误是否严重、是否满足业务成功率，必须同时看；失败率过高不能靠低价抵消。总费用还必须覆盖路由器、回退和验证器，不能只算最后一次成功调用。

响应速度也至少分两种：用户多久看到第一段文字，以及整个任务多久真正完成。关注 p95，即约 95% 的观测任务在此时间内完成。平均很快却有一批工单等很久，用户仍会觉得不稳定。串行回退增加尾部延迟；并行请求多个模型减少某些等待，也会增加费用。

## 6. 回退必须区分“失败”与“不知道是否成功”

模型服务限流或短暂故障，可以在有界重试后回退，受统一的时间、次数和预算限制约束。参数错误、权限不足应修正原因，换模型通常无效。

最危险的例子是：“修改工单状态”调用超时。超时只证明客户端没及时收到响应，不能证明服务器没有完成修改。此时应使用幂等键、查询操作状态或业务版本校验，再决定是否重试。换模型也不能解决重复执行问题，见 [第 03 篇](03-tool-call-hitl-security.md)。

## 7. 面试怎样回答

**问：怎样降低 Agent 成本？**

先定义质量和安全门槛，再测每个成功任务的总费用；从轨迹找出重复上下文、无效工具调用和重试等主要消耗。先减少无效工作，再评估缓存和模型路由。把新方案与基线在同一批任务上比较，检查成功率、错误类型与 p95，而不是只比较每百万 token 单价。

**追问：为什么不用最便宜模型先试一次？**

因为“先试”本身有费用和等待，还需要可靠的失败识别。若它经常给出看似正确的错误答案，系统可能根本不会升级。仅当识别与回退后的整体收益经验证成立时，这种策略才合适。

## 8. 小练习

**题目：**切换模型后费用下降 20%，用户投诉变多，可以宣布优化成功吗？

**参考答案：**不可以。按任务类型检查正确率、遗漏率、越权及人工返工；查看回退与缓存是否计入费用；区分首字延迟和最终完成时间。成本优化成立的前提是满足预先定义的质量门槛。具体模型、账号可用性和当前价格以实际部署当天的官方文档及账单为准。
