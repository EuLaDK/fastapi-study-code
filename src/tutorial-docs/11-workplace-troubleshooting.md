# 11｜工作排查案例：从现象找到能验证的原因

> 资料查阅日期：2026-09-15。以下 10 个案例是教学构造，不是实际生产事故记录。方案适用于本教程的 FastAPI 工单助手，落地时要结合你的业务、数据权限和外部服务能力。

## 先学一个排查顺序

不要一看到错答案就立刻更换模型。先沿着实际链路定位：

```text
用户目标与身份
  -> 输入与当前任务状态
  -> 检索或工具选择
  -> 工具参数、授权与执行
  -> 实际返回和送入模型的内容
  -> 模型回答或下一步动作
  -> 业务结果与验收
```

在尽量不改变条件的前提下，每次提出一个可验证的原因，找到能区分它与其他原因的观察，再做最小修复。修复后用原失败案例和相邻场景回归。[第 09 章](09-harness.md)解释了为什么工具轨迹和业务验收比“看起来正常”更可靠。

### 最小排查记录

记录 `run_id`、步骤、脱敏后的工具名及参数摘要、身份范围标识、耗时、结果状态、证据版本、模型与提示词版本、是否需要审批、最终业务对象 ID。对于写操作，记录幂等键和远端操作 ID；对于模型调用，记录用量与可用的缓存统计。

这些是建议字段，不要求先搭建一个观测平台。日志只留排查所需信息：避免把访问令牌、密码、整份客户资料或完整提示词无差别写入。OpenAI 官方安全文档也提醒工具参数和输出可能包含敏感数据，并建议控制提示词日志与访问范围。[S1]

| 现象 | 最先看什么 | 对应案例 |
|---|---|---|
| 回答有引用却错了 | 真正送入模型的片段与版本 | 1 |
| 不断重复工具调用 | 观察结果是否进入下一轮 | 2 |
| A 客户看到了 B 客户内容 | 查询、缓存和会话的租户边界 | 3 |
| 同一回复发送两遍 | 超时后的提交状态与幂等键 | 4 |
| 费用或延迟突然升高 | 每任务调用数、用量、缓存和耗时分解 | 5 |
| MCP 连接正常却不能调用工具 | 发现、协议、授权和参数分别检查 | 6 |
| 浏览器点错或状态不一致 | 当前页面、登录身份、动作后状态 | 7 |
| 长任务忘记约束 | 摘要、任务状态和原始授权记录 | 8 |
| Skill 没生效或越界 | 是否加载、是否适配、能力是否存在 | 9 |
| 说完成了但业务没生效 | 远端持久化结果，而非最终文字 | 10 |

## 案例 1：知识库里明明有答案，助手仍然答错

**现象：** 当前政策允许满足条件的 7 日内退款，助手却引用旧政策说 3 日。以下天数仅为教学例子。

**可能原因：** 新文档没入索引；召回了旧版本；新版本被筛选掉；实际输入被截断；新旧资料并存时模型没有正确判断有效期。

**如何区分：**

1. 直接核对源文档是否已更新及其生效条件，不能只看文件修改时间。
2. 保存本次召回候选的文档 ID、版本与片段，检查新政策是否出现。
3. 对比筛选后的结果与实际模型输入，找出是否在排序、去重或预算截断时丢失。
4. 人工只提供正确且充分的政策片段，再问同一问题。如果仍错，检查规则适用条件与生成步骤。

**修复方向：** 索引同步失败就修同步；旧版本占优就明确版本与有效期筛选；证据被截断就调整上下文装配。若问题缺少购买时间、产品范围等必要条件，应补问而不是猜答案。

**验证：** 至少回归新旧政策、生效日前后、例外条款、缺少必要条件和无答案场景；分别检查证据覆盖与回答正确性。不要用“引用数量更多”替代正确性。

**依据：** [02 章](02-memory-rag-long-context.md)的检索/生成分层；原始 RAG 方法将外部检索与生成结合，但不保证检索内容本身正确。[S2]

## 案例 2：Agent 一直“再查一次”，停不下来

**现象：** 工单查询已成功，模型仍反复查相同工单，直到任务超时。

**可能原因：** 工具结果没加入下一轮输入；调用 ID 与结果关联错误；工具出错却返回空列表；完成条件模糊；目标缺少必要信息却没有补问分支。

**如何区分：** 沿 trace 比较每次工具名、参数、返回状态与下一轮实际输入。相同调用返回相同信息且没有新进展，才是循环信号；分页或有截止条件的轮询可以重复调用同一工具。

**修复方向：** 保证调用与结果正确对应；将“无数据”“无权限”“超时”区分成可理解的状态；为缺信息提供补问或转人工路径。设置调用超时、轮次及总预算，预算耗尽时报告阻塞原因。

**验证：** 模拟工具成功、空结果、无权限和持续超时。每种情况都要在限定范围内完成、补问或停止。检查正常分页不会被误判为循环。

**依据：** [09 章](09-harness.md)和 OpenAI 的运行循环文档。[S3] 只降低温度不能修复一条丢失的反馈链路。

## 案例 3：A 客户看到了 B 客户的工单

**现象：** 模型语气和格式都正常，但回答出现另一个客户的资料。这是数据访问失败，不能仅按回答质量处理。

**先控制影响：** 暂停有问题的跨用户查询或缓存路径，保留必要的脱敏调查证据，按组织的数据事件流程处理。不要让模型继续查询其他客户来“验证泄漏”。

**可能原因：** 工具信任了模型提供的 `tenant_id`；检索未按权限限制；会话复用了其他用户状态；缓存键缺少租户与权限维度。

**如何区分：** 对照服务端认证身份、数据库查询条件、检索返回 ID、缓存命中键与会话归属。只在同一个环境用合成的 A/B 租户测试，确认数据在哪个边界混入。

**修复方向：** 在服务端授权层从可信身份推导范围，对查询和结果都落实必要检查；缓存不能跨授权范围复用，权限变更需使相关缓存失效。不要把越权数据先交给模型，再指望提示词要求它忽略。

**验证：** 合成 A/B 租户、同名文档、猜测对象 ID、角色变化、缓存命中和会话恢复案例；断言未授权内容没有进入模型输入，而不只是最终回答没显示。

**依据：** [03 章](03-tool-call-hitl-security.md)的授权边界。MCP 的授权机制也不能自动替代业务系统的对象级授权。[04 章](04-mcp-chrome-devtools-cdp.md)

## 案例 4：网络超时后重试，同一回复提交了两次

**现象：** 第一次请求超时，Agent 重试后显示成功，但工单里出现两条相同回复。

**本质原因：** “没有收到成功响应”与“服务器没执行”不是同一件事。

```text
客户端发送回复
服务端写入成功
响应在网络中丢失
客户端超时后用新请求再次提交
服务端又写入一次
```

**如何验证：** 比较两次请求的业务操作 ID、幂等键、目标与正文，查服务端提交时间和记录。若第一次已落库，应归类为响应不确定，而不是业务失败。

**修复方向：** 同一个逻辑操作使用稳定幂等键，并在服务端持久化去重结果；相同键配不同正文要拒绝，不能静默覆盖。并发请求时，去重检查与业务写入要有事务或可靠的原子约束，不能仅做“先查再写”。

如果外部服务不支持幂等，优先查询远端操作状态；无法判断时标记为待核对。发送邮件等动作未必能撤销，应在设计时明确补偿或人工处理路径。

**验证：** 在“提交前失败”“提交后丢响应”“两次并发重试”“本地 checkpoint 写入前崩溃”等节点注入故障，确认业务只发生一次或明确进入待核对状态。不能只测正常返回。

**依据：** [03 章](03-tool-call-hitl-security.md)、[06 章](06-tui-lsp-snapshot-runtime.md)。HTTP 的幂等语义有助于判断重试，但普通业务 `POST` 不会因为 Agent 加了重试就自动幂等。[S4]

## 案例 5：换了“更便宜”的模型，账单却涨了

**现象：** 单价下降，但平均任务消耗和 p95 延迟上升。

**可能原因：** 工具误选导致更多回合；失败后升级模型；更长输出或推理消耗；提示词前缀变化使缓存命中下降；多 Agent 重复读取同一份资料；工具本身收费。

**如何区分：** 在同一批代表任务上拆分“每轮用量 × 轮数”、缓存读写、工具次数、回退次数与人工复核成本；同时拆分排队、检索、模型和工具耗时。不能拿不同难度任务的平均值直接比较。

**修复方向：** 先减少无效回合和不必要的上下文，再决定路由。工具延迟是主因时，换模型帮助有限；模型误选工具时，可缩小工具集、改清描述或为困难步骤使用更合适的模型。

**验证：** 同时报告成功率、全部尝试费用/成功任务数、端到端 p50/p95 和严重失败。核对缓存写入与读取费率；推理 token 已计入输出用量时不要再加一次。

**依据：** [07 章](07-multi-model-switching-cost.md)的当前官方计费资料。本文不使用固定真实单价，因为模型与计费条款会更新。

## 案例 6：MCP 服务器“连上了”，却调用不了工具

**现象：** 网络可达或进程启动成功，但 Agent 看不到工具，或每次调用都失败。

**可能原因：** 只验证了传输层；客户端与服务端协议版本或功能不兼容；工具发现结果不同；令牌目标或权限范围不正确；模型参数不符合工具 schema；工具内部的业务 API 出错。

**如何区分：** 分层观察：传输可达 → 协议能力与工具发现 → 授权结果 → 工具名和参数 → 工具内部错误。使用客户端实际支持的协议流程；不要直接复制旧版本教程中的握手或传输假设。

**修复方向：** 对齐客户端、服务器支持的版本和能力，核对工具元数据与服务端校验，确认令牌受众和范围。启动命令成功不代表远端业务身份正确；也不能通过无条件转发另一服务的令牌解决授权错误。

**验证：** 用无副作用的工具测试成功路径，再测试无权限、过期凭证、非法参数与业务超时；错误应定位到对应层。日志中不要输出原始令牌。

**依据：** [04 章](04-mcp-chrome-devtools-cdp.md)列出截至查阅日的 MCP 规范变化与安全来源；协议本身不等于某个具体工具实现。

## 案例 7：浏览器操作点错按钮，或看到的页面与后端不一致

**现象：** Agent 说点击了“保存”，实际点到另一个相同按钮；或者页面显示旧状态，但后端已更新。

**可能原因：** 使用旧页面快照中的位置或元素编号；同名按钮不唯一；页面仍在加载；登录到错误账号或环境；前端缓存、异步保存或乐观更新掩盖了真实结果。

**如何区分：** 核对当前 URL、工单 ID、登录身份和页面状态；查看相关网络请求、响应、控制台错误，再对照后端真实记录。不要把“页面上出现成功提示”作为唯一业务证据。

**修复方向：** 操作前基于当前页面定位，优先使用稳定语义并限定所在区域；操作后等待与任务相关的明确状态，而不是任意固定睡眠。已经超时的写操作先核对结果，避免盲目再次点击。

**验证：** 覆盖慢网络、同名按钮、弹窗遮挡、页面刷新与提交响应丢失；确认不会提交到错误工单。需要模拟危险动作时使用测试账号和合成工单。

**依据：** [04 章](04-mcp-chrome-devtools-cdp.md)的浏览器能力边界，以及[06 章](06-tui-lsp-snapshot-runtime.md)对状态快照范围的区分。定位策略属于本教程的工程建议。

## 案例 8：任务进行很久后，Agent 忘记“只生成草稿”

**现象：** 早期用户限制只写草稿，压缩或恢复后，Agent 打算直接提交回复。

**可能原因：** 重要约束只存在聊天历史；摘要丢失否定条件；旧总结把“计划提交”改写为“已批准”；不同用户或任务共用了状态。

**如何区分：** 对照原始用户请求、压缩前后摘要、结构化任务状态与实际审批记录。确认执行端是否把模型生成的 `approved: true` 当成了授权。

**修复方向：** 将目标、禁止动作、待确认项保存在可追溯的任务状态中。执行端从可信记录验证批准的用户、目标、内容和版本；模型记住规则有助于决策，但即使它忘了，写工具也必须拒绝未授权提交。

**验证：** 人为压缩历史、重启进程、恢复旧状态、替换草稿内容，检查未获匹配授权时仍然不能写入；允许读取和起草的正常能力应保留。

**依据：** [02 章](02-memory-rag-long-context.md)、[03 章](03-tool-call-hitl-security.md)、[09 章](09-harness.md)。上下文摘要和安全授权是不同责任。

## 案例 9：写了 Skill，却没触发或效果越来越差

**现象：** 新增“工单排查”技能后，助手仍不知道操作步骤；或者一加载就给所有任务套用同一个流程。

**可能原因：** 宿主未发现技能；名称和描述不能表达适用范围；格式不被支持；正文过长或含冲突要求；资源路径无效；技能依赖的工具根本不存在。

**如何区分：** 先查宿主实际发现、选择和读取了哪些内容，再检查工具能力与引用资源。未加载时，继续改正文通常没有意义；已加载但冲突时，继续加规则可能让情况更差。

**修复方向：** 明确触发条件与输出标准，保留核心步骤，把详细资料按需引用；修正宿主支持范围内的格式与资源路径。不要把“查询所有工单”这类文字当作扩大权限的方式。

**验证：** 准备应触发、不应触发、资料缺失、工具不可用、外部资料包含恶意指令五类例子。既检查任务质量，也检查是否过度触发和越权。

**依据：** [05 章](05-prompt-skill-prompt-engineering.md)与 Agent Skills 当前规范。[S5] 开放格式有助于复用，不保证每个宿主支持全部可选功能。

## 案例 10：模型说“完成了”，测试也没报错，但功能不工作

**现象：** 工单状态未更新，或者生成的 FastAPI 接口在真实页面中返回错误。

**可能原因：** 只生成代码或草稿，没有执行提交；HTTP `202 Accepted` 被误当作已完成；测试用的是另一个环境；LSP 无诊断被误当作业务测试；缺少真实链路的验收。

**如何区分：** 从真实业务对象往前追：对象在哪个库、哪个租户、哪个版本？是否有提交结果 ID？异步任务是否完成？测试覆盖了哪条请求路径？是否使用了能掩盖错误的 mock？

**修复方向：** 把“完成”定义成可观察的业务结果。查询接口要验证身份、参数、返回和错误情况；写操作要核对持久化结果。区分“已接收”“待审批”“执行中”“已完成”“失败/待核对”。

对于代码变更，静态诊断、单元测试和端到端检查各自覆盖不同问题，选择能验证这次改动的检查。例如鉴权错误就测跨用户访问，异步状态问题就测任务完成后的查询，不必每次无差别跑全部系统。

**验证：** 故意让远端拒绝写入、异步任务失败、运行环境指错或返回陈旧数据，确认系统不会声称成功。再跑一个真实授权的成功路径验证验收规则没有过严。

**依据：** [06 章](06-tui-lsp-snapshot-runtime.md)、[09 章](09-harness.md)。HTTP 202 的语义是已接受处理，不保证处理已完成。[S4] Anthropic 的长任务案例也记录了缺少充分测试导致提前宣布完成的失败。[S6]

## 把一次排查变成下次能复用的经验

每解决一个问题，留下这六项就有价值：

```text
现象：用户看到了什么错误？
影响：涉及哪些对象、用户和时间范围？
证据：哪条记录或对照实验排除了其他原因？
根因：哪一个机制没有按预期工作？
修复：改动哪一层，为什么在那里修？
验证：哪些案例证明修复有效，哪些限制仍然存在？
```

把脱敏后的失败案例加入回归集合。不要只保存“换模型后好了”；要尽量知道是模型能力、输入变化、工具状态还是缓存差异造成了结果变化。评估指南强调用真实分布、边界案例和持续比较改进系统。[S7]
