# 06｜TUI、LSP、快照与运行时：助手“看起来会编程”的支撑系统

> 面向有 Python、HTTP/API 基础的 Agent 初学者。资料核查日期：2026-09-15。本文根据目录主题独立编写；截图中的 snapshot 和 runtime 没有唯一解释，因此明确区分几种常见含义。

## 1. 从“重开以后，为什么又发送了一次”开始

工单助手生成草稿、获批、发送回复。此时进程崩溃，重启后从旧记录继续，又执行了一次发送。界面显示“恢复成功”，客户却收到两封邮件。

这说明界面、程序状态、文件和外部业务结果不是同一个东西。**TUI 负责人机交互，LSP 提供代码语义能力，runtime 负责实际执行，snapshot/checkpoint 只保存其明确覆盖的状态。** 把它们都叫“Agent 的记忆”，就会忽略恢复边界。

## 2. 四个概念分别解决什么

| 概念 | 主要职责 | 不自动保证什么 |
| --- | --- | --- |
| TUI，终端用户界面 | 在终端显示消息、进度、审批、差异，接收键盘操作 | 不保证任务状态已持久化 |
| LSP，语言服务器协议 | 编辑器或工具与语言服务器交换语义查询及诊断 | 不保证程序运行正确 |
| Runtime，运行时 | 调度模型与工具，管理进程、文件、权限、超时和结果 | 不保证一切副作用可撤销 |
| Snapshot / Checkpoint | 保存某一范围、某一时刻的状态以支持检查或恢复 | 不保证外部世界一起回滚 |

TUI 是界面形态，不是必须采用的架构；同一个执行系统也可以用网页或 IDE 面板呈现。界面断开后任务是否继续，取决于进程托管和服务端任务管理，而不是有没有漂亮的进度条。

这里 runtime 指 Agent 的执行系统；在别的文章里，它也可能指 Python、Node.js 等语言运行时，阅读时必须结合上下文。

## 3. LSP：从“搜索同一串字符”到“找到同一个符号”

假设你准备修改 FastAPI 项目中的 `get_ticket`。文本搜索能找到这个名字，但可能包含同名函数、注释和字符串。语言服务器在其支持范围内利用语法、类型与项目结构，回答“这个位置的符号定义在哪、有哪些引用”。

LSP 标准化请求、响应和通知，典型能力包括 definition、references、hover、rename、diagnostics。客户端和服务端通过能力声明确定支持哪些功能，不是所有语言服务器都实现全部功能。[1]

```text
助手定位文件和位置
  -> LSP 客户端发送定义/引用查询
  -> 语言服务器结合已同步文档和项目环境分析
  -> 返回位置或诊断
  -> 助手读取相关代码，再决定修改
```

工程上的两个边界尤其重要：

- **上下文可能陈旧。** 编辑器缓冲区、磁盘文件和语言服务器已同步版本可能不同；诊断需要与目标文件版本对应。
- **静态分析有能力边界。** Python 动态导入、反射、运行时配置等可能使引用分析不完整；接口能否正确鉴权仍需要运行验证。

没有 LSP 时，文本搜索、编译器、类型检查器和测试仍可完成很多工作。已经出现复杂重命名或引用追踪需求时，再利用 LSP 的语义优势。

截至核查日，官网标注 **3.18 为 Current、3.19 为 Upcoming**。[1] 实际接入应看能力声明与实现版本，不应因官网出现新版本就假定本地服务器具备全部功能。

## 4. Runtime：命令不是发出去就算完成

执行 `python -m ...` 至少需要确定：工作目录、解释器、环境变量、可访问文件、网络权限、超时、退出码和输出。相同命令在不同虚拟环境中可能得到不同结果。

下面是**可直接执行的标准库自检示例**，只运行内联 Python；展示“输出”和“退出状态”需要同时处理，不修改项目文件：

```python
import subprocess
import sys

result = subprocess.run(
    [sys.executable, "-c", "print('ready')"],
    capture_output=True, text=True, timeout=5, check=True,
)
assert result.stdout.strip() == "ready"

failed = subprocess.run(
    [sys.executable, "-c", "raise SystemExit(2)"],
    capture_output=True, text=True, timeout=5,
)
assert failed.returncode == 2
```

`check=True` 会把非零退出状态转成异常；`timeout` 限制等待，并按 `subprocess.run` 的机制结束、等待该子进程。[2] 生产运行时还要考虑输出过大、子孙进程、持久任务与资源回收，不能把这段示例当完整沙箱。

参数列表默认不启用 shell，能减少拼接命令造成的注入风险；但这不验证被调用程序的业务参数，也不限制文件权限。Windows 的 `.bat/.cmd` 还有系统 shell 解析的特殊情况，必须按 Python 官方安全说明处理。[2]

判断任务是否完成，也不能只看退出码 0。测试进程成功表示指定检查通过；“邮件已发送”必须有发送系统的结果证据。这是执行成功与业务成功的区别。

## 5. 四种“快照”最容易混淆

| 状态载体 | 通常保存什么 | 恢复不了什么 |
| --- | --- | --- |
| 页面内容快照 | 当时可观察的页面结构、文本或元素标识 | 整个浏览器与后台数据库 |
| 工作区/文件系统快照 | 明确纳入范围的文件状态 | 未纳入的路径、外部 API 副作用 |
| Git 提交 | 提交中记录的文件内容及历史 | 未提交状态、忽略文件、数据库、邮件 |
| Agent checkpoint | 流程状态、消息、待处理节点及相关元数据 | 未显式纳入的文件、进程、第三方服务状态 |

“恢复快照”之前，先问：**保存了什么、何时写入、写到哪里、恢复会重跑哪些动作？** 名字相同不代表语义相同。

例如 LangGraph 的 checkpointer 按执行 super-step 保存图状态。super-step 可理解为一轮可执行节点及其状态汇合的边界；它不是任意 Python 行级别的进程内存快照。[3]

若使用内存保存器，进程退出记录就会消失；需要跨进程恢复时，必须使用实际持久化后端。当前文档也区分同步保存、异步保存、退出时保存等持久性选项，其性能与崩溃后的可恢复范围不同。[3][4]

## 6. 工单发送怎样才能恢复得可靠

建议把过程分成明确的业务状态：

```text
草稿已保存 -> 等待审核 -> 已批准 -> 发送结果待确认 -> 已确认发送
```

每个操作关联稳定的操作 ID；发送前保存待执行意图，发送后保存实际结果。恢复时先读取操作记录、核查外部结果，再决定继续等待、重试还是结束。

**“发送结果待确认”是必要的真实状态。** 客户端超时可能发生在外部提交之后；恢复旧 checkpoint 不会撤回邮件。可靠执行因此还依赖下游幂等支持、查询和对账，详见[第 03 篇](03-tool-call-hitl-security.md)。

LangGraph 的一个具体细节能说明为什么必须理解恢复机制：在节点中调用 `interrupt()` 暂停后，恢复会从该节点开头重跑，暂停前的代码可能再次执行。官方要求这部分副作用具备幂等性，或调整节点和审批位置。[5] 把发送放到审批之后能避免未批准发送，却仍不能消除“发送完成后进程崩溃”的重试问题。

## 7. 面试与练习

**题：有 checkpoint，是不是就实现了事务和恰好一次执行？**

回答要区分状态范围：checkpoint 恢复的是工作流已保存状态；数据库事务约束数据库内的一组操作；外部邮件等副作用需要其自身的幂等或补偿机制。单个 checkpoint 无法自动原子提交所有外部系统。

**练习：助手修改了文件 A，发出一封邮件，然后恢复到修改前的 Git 提交。哪些动作被撤销？**

答案：若明确把工作区相关文件恢复到该提交，提交覆盖的文件内容可恢复；邮件仍然存在。Git 提交本身也不会自动处理未跟踪或忽略文件。若还恢复了 Agent checkpoint，工作流可能重新执行发送，反而增加重复副作用风险。
